## 两项 Windows 多开交付门槛

### 状态目录隔离没有覆盖 Windows 的路径来源

1.7.7 `commands.rs` 将 worker 设置写入实例 `worker-home/.codex-session-delete/settings.json`，对子进程设置 `HOME`、`CODEX_HOME`、`CODEX_SQLITE_HOME` 和独立端口。

但 `paths::default_app_state_dir()` 通过 `directories::BaseDirs::new().home_dir()` 获取状态目录；`SettingsStore::default()`、`StatusStore::default()` 和 launcher 默认设置加载沿用它。锁定的 `directories 6.0.0` Windows 实现调用 `dirs_sys::known_folder_profile()`，最终使用 Windows `SHGetKnownFolderPath`，不读取该 `HOME`。

只读探针在隐藏 PowerShell 子进程设置假的 HOME 后，返回：

```text
ChildHome=D:\Programming\Projects\CodexPlusPlus\target\temp\v177-isolated-home-probe
WindowsProfile=C:\Users\29035
```

证据：`target/temp/v177-windows-known-folder-probe.json`。没有启动 Codex 或多开 worker，没有读写真实设置。

因此源码路径链表明 worker 默认设置和状态仍可能落到主实例目录，隔离设置文件没有被默认读取。`CODEX_HOME`、SQLite 和 user-data 的单独配置不能解决 Codex++ 自身状态路径问题。

实施应在现有路径入口明确传入/选择 worker 状态根目录，主实例保持原默认；不要靠修改用户级环境变量或伪装整个 Windows 用户目录。必须覆盖主实例与两个不同供应商 worker 同时运行、设置与 status 不串写、目录不存在时失败边界及主实例不受影响。

### Windows worker 退出校验直接返回 true

1.7.7 `commands.rs::multi_worker_process_matches` 的 Windows 分支忽略 options_path 并返回 true；`terminate_multi_worker` 随后执行 `taskkill /PID <pid> /T /F`。实例 manifest 保留 worker PID，旧 worker 退出后 PID 被其他进程复用时，后续停止/重启可能针对错误进程。

上游身份匹配测试仅在 `cfg(unix)` 下运行，Windows workspace 全通过也不能证明此分支安全。实施前需确认 PID 对应当前主程序、worker 标记及当前实例参数路径，并测试无匹配、PID 复用、已退出进程和仅结束指定实例。不能通过隐藏多开入口或跳过测试交付。

两项属于源码审查发现的明确缺口；本轮没有启动新 worker 来复现事故。评估时发布后的两项修复未触及这些路径，未发现当前已合并补丁覆盖它们。
