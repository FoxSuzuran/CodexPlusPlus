## 结论

## 当前客户端的并发候选

只读检查安装包 `app.asar` 中的 `webview/assets/app-shared-40678a67f0e3.js` 和 `app-initial-25361a10f2bf.js`：

1. 既有会话的 Plan 选择通过 `updateThreadSettingsForNextTurn` 提交，设置请求按会话串行。
2. Plan 选择组件暂存本组件的乐观模式；请求结束后清除它，重新依赖会话状态。
3. `applyThreadSettings` 发送设置请求前保存 `latestThreadSettings` 的对象引用。成功返回后，仅当当前对象仍是同一个引用时才执行本地回填。
4. 如果等待期间其他通知替换了该对象，成功响应可以跳过回填。正常的 Plan 通知也会替换对象，此时跳过可能完全正确；只有缺失、迟到或竞争通知导致模式没有同步时，才可能形成实际失败。

从安装包提取实际 `applyThreadSettings` 方法，在隔离对象中检查两个条件；请求、通知和状态操作均使用模拟接口，没有操作真实会话：

| 模拟条件 | 方法返回 | 本地回填 | 隔离对象中的模式 |
| --- | --- | --- | --- |
| 等待期间无其他设置通知 | 成功 | 执行 | Plan |
| 等待期间一条无关服务档位通知替换设置对象 | 成功 | 跳过 | Default |

这是对**跳过回填条件的复现**，不是对真实点击到错误注入全过程的复现。真实客户端可能继续收到正确的 Plan 通知；现有日志不足以确认失败发生时的通知顺序。

## 稳定修复应落在哪里

先用同一次失败的证据区分下列情况，再修共同入口：

| 实际失败状态 | 修复位置与原则 |
| --- | --- |
| 界面选择 Plan，`turn/start` 却为 Default | 官方客户端的设置同步、模式选择与发送准备链路。按会话跟踪选择及设置版本，等待更新完成后核对最终模式；更新失败要明确反馈，不能静默使用旧模式 |
| 后台为 Plan，模型可见历史仍为 Default | 官方 app-server 的 world-state 差异生成、压缩与恢复链路。比较当前渲染指令的哈希，未知状态重新生成 developer 模式片段；沿用 #39163/#45519 的原则 |
| 本地 Plan 指令正确，供应商收到的内容缺失 | 按实际启用的 Responses、Chat 或 Messages 协议核对转换及供应商处理，不改界面或会话状态来掩盖下游问题 |
| 供应商收到正确 Plan 指令，模型仍执行 | 属于模型遵循问题。重复注入不能提供保证；需要单独核对工具执行约束，不能称为模式参数修复 |

并发回填路径不能直接删除对象引用保护，否则可能用旧请求覆盖用户之后的新设置。应根据请求触及的字段及会话版本合并，并以最新选择为准；已有等待机制也应复用。

需要覆盖的回归场景：已有会话连续 Plan 回合、Plan → Default → Plan、等待时发生无关设置通知、快速切换与立即发送、设置请求失败、恢复会话及压缩后首回合。修复要同时检查最终请求模式和模型可见 developer 片段，不能只断言徽标。

## 临时恢复与下一次复现

临时可尝试在全新会话中开启 Plan，等待模式显示和设置加载完成后再发送，以避开旧会话恢复状态。它不是所有根因的保证。

旧会话若需要重新建立模式片段，可先关闭 Plan，发送一条仅确认模式的消息，再开启 Plan 并发送；只快速关闭再开启而不产生中间回合，未必建立新的历史基线。

下次偶发时，先保留失败线程和准确发生时间，避免立即切换模式、重启或清理历史。应对照同一回合的：

- 点击选择及最终界面模式；
- 设置请求完成、失败和通知顺序；
- `turn/start.collaborationMode`；
- `task_started`、`turn_context` 的模式；
- 压缩后实际保留的最近 `<collaboration_mode>` developer 片段。

诊断只需要模式、指令是否存在及哈希，不需要记录完整提示词或凭据。

## 后续实现与交付

修复位于 `assets/inject/renderer-inject/70-model-catalog.js`，按原清单重新组装 `assets/inject/renderer-inject.js`。

原生 RPC 方法不可写，补丁复用现有 AppScope 能力发现，接管可写的 `forHost` 注册表，仅包装本机会话 RPC。其他主机仍返回原始对象；没有修改安装包源码、权限选择、模型授权、扩展写能力或依赖。

同一会话最新一次 Plan/Default 选择作为本地版本标记：

1. 原生设置更新仍立即进入现有队列，不增加服务器设置请求。
2. 首次发送等待最新模式选择及其后的设置更新。读取期间再次选择模式或更新模型时，重新核对最新标记。
3. 读取一次原生会话快照，把确认的模式显式写入首条发送请求，避开原生本地回填被跳过后继承旧模式的路径；沿用请求及会话中的模型、推理档位、原生模式指令。普通发送和 `startEmptyTurn` 原生继续入口使用同一检查。
4. 更新返回 `false` 或抛错时，保持原返回值/异常，提示重新选择模式，并阻止使用旧模式发送。后来的成功选择可以恢复发送。
5. 首条发送成功后移除本地标记；发送失败则保留，便于重试。空回合可能无操作返回，需再读取一次原生模式，确认同步后才清除标记。期间产生的新选择不会被前一条发送完成操作清除。

普通发送、未跟踪模式选择的旧会话及后续回合不增加会话读取或网络请求。首条发送的快照读取是本机 RPC，不调用模型供应商；没有固定等待时间。独立指定 `inheritThreadSettings=false` 的请求，以及 durable/非用户来源会话，保留原生行为。

可调用 RPC Proxy 的 `.bind` 属性也会成为远端方法路径，因此转发使用标准 `Function.prototype.bind.call`，不读取远端 `.bind`。
